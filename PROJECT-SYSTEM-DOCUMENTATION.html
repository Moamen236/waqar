WAQAR — Unified System Specification

This document merges the E-Commerce documentation (storefront & customer journey), the Internal Operations documentation (admin, warehouse, delivery, accounting, treasury), and an inventory of the frontend HTML template into one coherent specification for WAQAR — surfacing conflicts, gaps, and decisions needed before any development starts.

01

Project Overview

WAQAR is a single-store fashion e-commerce platform (Laravel · Inertia.js · React · TypeScript · Tailwind CSS) with a full customer storefront on top, and a complete internal operations layer underneath — order checking, delivery management, accounting, treasury, and employee management — layered onto the same orders/products/inventory without changing the customer's shopping experience.

✅ Confirmed — Core design principle (stated explicitly in both documents)

"Do not change the existing e-commerce customer journey." The customer always experiences: Browse → Cart → Checkout → Cash on Delivery → Order. Everything else — Checking, Delivery Manager, Representatives, Shipping Companies, Accounting, Treasury — is an internal layer that activates automatically once an order is created, and is invisible to the customer.

02

Business Rules (Consolidated)

Merged from both source documents. Rules in bold are new or clarified by the Internal Operations document and were not present (or were vaguer) in the E-Commerce document.

Product

  • Products do not have brands.
  • A product has one or many variants (size/color/etc.); stock belongs to the variant, not the product.
  • Products can belong to multiple categories (nested categories allowed, many-to-many — Section 05) and to many independent collections.
  • A product has a lifecycle mode: Advertisement (no inventory tracking) or Real (inventory tracked) — same product record converts between the two without creating a new product.

Inventory

  • Inventory is tracked per (warehouse × variant); available = physical − reserved.
  • An order reserves stock at creation; it does not deduct physical stock.
  • Physical stock is deducted only when Accounting confirms the order as "Delivered." Not at order creation, not at Checking confirmation, not at shipment/assignment.
  • Architecture must support multiple warehouses from day one, even though the business currently operates one.

Payment

  • Customer checkout supports Cash on Delivery only. No online payment gateway, no card storage.
  • No sales tax is calculated anywhere in the system.
  • Internally, Accounting records money movement in Cash / Bank Transfer / Wallet / Other as it actually arrives (from representatives, shipping companies, or bank transfers) — this is a back-office reconciliation concern, not a customer-facing payment option.
  • All financial calculations (price, discount, shipping, totals) happen server-side; the frontend never controls them.

Shipping

  • Shipping rate resolves from Country → Governorate → City → District → Area; a rate can be configured at the Governorate, City, District, or Area level, with the most specific match winning. The frontend cannot set the final price — the server always resolves it (Section 11).
  • Delivery execution happens via either a Delivery Representative or a Shipping Company, assigned by the Delivery Manager after Checking confirms an order.
  • Shipping companies charge configurable delivery fees and return fees, reconciled against what they actually transfer to the business.

Order Handling

  • Customer-facing order number starts at 1001 and is independent of the database primary key.
  • Orders may originate from the Website or from Customer Service (manual/phone order) — both enter the same operational workflow after creation.
  • Every order status change must be recorded in a permanent history (never overwritten).
  • Order Status, Payment Status, Inventory Status, Delivery Assignment, and Customer-Facing Status must be stored as separate concerns, never collapsed into one status field.

Explicitly Out of Scope (v1)

  • Brand management, product zoom.
  • Social/OTP login (Google, Apple, Facebook, OTP).
  • Tax, online payment gateways, SMS/WhatsApp, live chat, AI assistant.
  • Generic CMS / page builder.
  • Multi-currency, multi-store, multi-vendor, loyalty points, gift cards, store credit (all listed as future enhancements in both docs).

✅ Decided — Customer Service acts as the customer, not as a separate order path

Customer Service does not get its own order-creation logic. It calls the exact same CreateOrderAction as the storefront checkout (Section 08) — same validation, same server-side price/shipping/discount calculation, same COD payment record, same inventory reservation. The employee is simply typing in what the customer told them over the phone, in place of the customer typing it in themselves. This is also why Customer-Service orders are always COD at order time (Question 13) — there is no separate payment path to build.

✅ Decided — one global role/permission system for both flows

There is a single, merged role & permission catalog (Section 15) covering the entire system — not one set of roles for "e-commerce/admin" and another for "internal operations." ✅ Resolved — both fields added: product_type and inventory_tracking_enabled

The original gap: the E-Commerce document's products table has no field to represent Advertisement vs Real, so there was nothing for the checkout/inventory flow to check.

Resolution — two fields, kept in sync, each doing a different job:

  • product_type: advertisement | real — the business-facing classification. This is what Chairman/Vice Chairman see and set; the "Convert Advertisement Product to Real Product" action (the flow diagram above) flips this value.
  • inventory_tracking_enabled: boolean — the operational flag the checkout/inventory logic actually checks in the hot path. Set automatically whenever product_type changes (false while advertisement, true once real) — never edited independently by a user.

Why both instead of one: product_type reads cleanly in admin screens and reports ("12 Advertisement products, 340 Real"), while inventory_tracking_enabled is a plain boolean the CreateOrderAction's stock-validation step can check directly — if (!inventory_tracking_enabled) skip stock check — without a string comparison on every checkout. Checkout flow: for each order item, if the variant's product has inventory_tracking_enabled = false, stock validation and reservation are bypassed entirely for that item; if true, the normal available-quantity check and reservation (Section 07) applies as usual.

✅ Resolved — categories are many-to-many, to support catalog scale

The original question: the E-Commerce document implied a single category per product (products.category_id), while typical fashion catalogs often need multiple categories per product; Collections already cover multi-grouping, so single-category might have been intentional.

Resolution: to build the system correctly for scale, products.category_id is dropped in favor of a product_categories pivot table (product_id, category_id), the same pattern already used for Collections. A product can now be filed under as many categories as merchandising needs — e.g. listed under both "Men → Shoes" and a cross-cutting "Sportswear" branch — without relying on Collections to fake multi-category grouping. Category-based storefront filtering/browsing (Section 08's Product Listing) and admin category management both query through this pivot instead of a single foreign key.

Weight-Based Variants

Both source documents use the word "weight" for two different things. This needs to be resolved before the schema is finalized.

Meaning A — Sizing guide (customer body weight)

Both documents' variant examples use weight ranges as a size recommendation — "if your body weight is in this range, this size fits you."

T-Shirt
Black/S → 70–85 kg
Black/M → 85–100 kg
White/L → 100–130 kg

Internal Ops doc explicitly confirms this must be per-variant, not per-Size master record, because the same "S" means a different weight range on a different product.

Meaning B — Shipping/package weight

The Internal Operations document separately lists weight as a factor that shipping pricing may depend on (alongside governorate, representative, shipping company, item count, delivery type) — this is the physical package weight used to price a delivery, unrelated to body-size fit.

The E-Commerce document's shipping model, by contrast, is purely area-based (Country → Governorate → City → Area → flat Rate) with no weight factor at all.

✅ Resolved (Question 1) — one field, one purpose: sizing only

The original conflict: a single weight_min/weight_max field would have been read by the storefront as a size-fit helper while Internal Operations expected a "weight" value to price shipping — the same field can't serve both purposes, and the E-Commerce document's shipping_rates table had no weight/tier field at all to receive it.

Resolution — the full process is implemented exactly as speced for sizing, with no shipping use at all: variant.size_guide_weight_min / size_guide_weight_max is built purely as a customer-facing sizing helper, shown on the product page's "Size Guide." It is never read by pricing logic. Shipping is priced entirely by geography (Governorate/City/District/Area — see Section 11) — weight plays no role in shipping cost at all. No shipping_weight_kg field is added to the schema; if weight-based shipping is ever wanted in a future phase, that would be a separate, later schema change, not a reuse of this field.

✅ Resolved — stock deducts only when Accounting confirms "Delivered"

The original conflict: the E-Commerce document's reservation example showed stock decreasing when the order is "fulfilled," without defining that moment precisely. The Internal Operations document is explicit: physical stock is deducted only when Accounting confirms "Delivered" — not at order creation, not at Checking confirmation, not at shipment or assignment to a representative/shipping company.

Resolution — the whole system works off this single rule, with no other deduction point anywhere:

  • Order created (Real product) → reserve stock. No deduction.
  • Confirmed / Postponed / Backorder / Assigned / Out for Delivery → reservation unchanged. Still no deduction.
  • Cancelled, or Returned-at-delivery → release reservation, no deduction ever happened.
  • Accounting confirms Delivered → this is the only point that deducts physical stock: create an inventory_movements row of type sale, release the reservation.
  • Partially Returned at delivery → deduct only the kept quantity; release reservation on the rest.
  • Post-delivery return, received & inspected as sellable → add stock back (inventory_movements type return).

✅ Resolved (Question 12) — Cash on Delivery is the only payment method; no card data is ever collected

The original conflict: checkout.html and checkout2.html render radio options for Credit Card, PayPal, and Apple Pay alongside Cash on Delivery, complete with card-number/expiry/CVV sub-fields. Both source documents are explicit: "Only Cash on Delivery is supported... No online payment gateway is required" and this is listed under Explicitly Excluded Features.

Resolution: every non-COD option, and every card-number/expiry/CVV sub-field, is removed entirely from the checkout template for v1 — the storefront collects no card or payment-gateway data at all, from any customer, at any point. This also keeps the system out of PCI-DSS scope, since no cardholder data ever reaches the application. Could be re-introduced later behind a feature flag if the business ever adds a gateway, but that is out of scope for this build.

✅ Resolved — checkout address rebuilt to the Country → Governorate → City → District → Area flow

The original conflict: the template's checkout fields are a generic Country / State / City / Postal Code, with a free-text shipping estimator on the cart page — it doesn't match the required shipping hierarchy at all.

Resolution: the generic fields are replaced with four dependent dropdowns — Governorate, then City, then District, then Area — each populated from the previous selection (/api/shipping/governorates, /api/shipping/cities?governorate_id=, etc., per the E-Commerce document's Shipping API endpoints, extended with a districts endpoint). The free-text shipping estimator on the cart page is replaced the same way: as soon as the customer picks far enough down the cascade to hit a level that has a configured rate, the server returns the resolved shipping price (Section 11's Area → District → City → Governorate fallback) — the customer never types or edits a price. Postal Code is dropped; it isn't part of either source document's address model.

✅ Resolved — add /admin/orders/create

The original gap: Internal Operations requires Customer Service to be able to create an order on a customer's behalf (phone order), entering the same workflow as a website order. The E-Commerce document's Admin Pages list had no /admin/orders/create — only /admin/orders (list) and /admin/orders/{order} (show).

Resolution: /admin/orders/create is added to the Admin Pages list, gated behind an orders.create permission (Customer Service and Customer Service Team Leader roles). It reuses the exact same CreateOrderAction, validation, pricing/shipping calculation, and COD payment record as the storefront checkout — this is Flow 2 from Section 03. The screen lets the employee: search for an existing customer or create a new one, pick products/variants, select the Governorate → City → District → Area address (Section 11), review the server-calculated total, and confirm — producing an orders row with order_source = customer_service and created_by_employee_id set, identical in every other respect to a website order.

09

Payments

✅ Resolved — one global payment_status; collection detail is captured only when "collected"

The original conflict: the E-Commerce document uses payment method cod only, with payment_status ∈ {pending, collected, not_collected, refunded}. The Internal Operations document uses payment method Cash / Bank Transfer / Wallet / Other, with payment status Paid / Partially Paid / Unpaid, manually recorded by Accounting.

Resolution: payment_status stays exactly the E-Commerce document's four values — pending, collected, not_collected, refunded — as the single global status. "Unpaid" (Internal Operations terminology) is just the internal-facing label for pending; it is not a separate value. Only when Accounting sets an order to collected do two extra fields on that same payment record get filled in:

  • collection_type: full ("Paid Total") or partial ("Partially Paid") — how much of the order was actually collected.
  • collected_method: cash | bank_transfer | wallet | other — how Accounting actually received the money (via a representative, a shipping-company transfer, or directly).

The customer never sees or chooses any of this — payments.method stays cod for every order, always. collection_type and collected_method are Accounting-only fields, left empty until the order is collected. No separate settlement/reconciliation table is needed: the existing treasury_transactions table (already in the E-Commerce document, with reference_type/reference_id) records the actual money movement into the Cash/Bank/Wallet account, referencing this payment.

Shipping

Geographic hierarchy: Country → Governorate → City → District → Area. District is added as an explicit level between City and Area, matching the Internal Operations document's terminology (the original E-Commerce document's hierarchy stopped at Area).

✅ Decided — shipping pricing depends on Governorate / City / District (resolves the "pricing inputs" conflict)

The original conflict: the E-Commerce document priced shipping by Area only; the Internal Operations document listed Governorate/City/District (plus representative/company, weight, item count, delivery type) as potential pricing inputs, with no table to support any of it.

Resolution: shipping_rates becomes level-flexible instead of Area-only. Each rate attaches to exactly one geographic level — Governorate, City, District, or Area — via a geo_type + geo_id pair (or four nullable FKs, whichever is cleaner in Laravel). At checkout, the server resolves the rate by checking the most specific level first and falling back upward:

Area rate exists?
→
District rate exists?
→
City rate exists?
→

Lets the business start with one broad rate per Governorate and progressively override with cheaper/pricier City, District, or Area-specific rates only where needed — instead of being forced to price every single Area individually.

The frontend still never sets or sees a price before the server calculates it — only the resolution logic behind shipping_rates changed. Representative/company-specific fee overrides, weight, and item-count multipliers remain deferred to Phase 2, unchanged from the existing Question 10 decision — only the geographic granularity moved into v1.

✅ Decided (Question 20) — locale is routed by URL prefix, enforced by middleware

The active language is determined by a {locale} route segment, not a hidden session value — /ar/... and /en/... wrap every storefront route (/ar/shop, /en/shop, /ar/product/{slug}, /en/product/{slug}, …), and identically /ar/admin/... / /en/admin/... wrap every admin route, applying the same mechanism to both areas per this section's "never a separate architecture" principle above.

  • A dedicated SetLocale middleware reads the {locale} segment, rejects anything that isn't ar/en, calls App::setLocale(), and drives the <html lang dir> attributes (above) on the response. The URL is the single source of truth for which language renders — two people can share an /en/product/{slug} link and both see English, regardless of each other's session.
  • A bare / (no locale segment) redirects to /ar/ or /en/ — Arabic by default, or the visitor's last explicit choice if a lightweight preference cookie is set from a previous visit. This is what "persisted per session (guest) or account (authenticated)" in the E-Commerce document now means in practice: it decides where a bare hit redirects to, not what renders at a given URL.
  • The locale switcher navigates to the sibling URL under the other prefix (swap the segment) rather than re-rendering the same URL with different content — every page stays independently crawlable, shareable, and bookmarkable per language, which a session-only switch can't give an e-commerce storefront.

Question 16 ✅ Decided

Customer Service agents can grow beyond a single flat group — should a Customer Service Team Leader tier exist, and if so, what do they see?

DecisionYes — add a Customer Service Team Leader role, plus a team_leader_id on employees. Regular agents on the base Customer Service role are unaffected: their visibility stays as already defined, global and unscoped. Full policy: Section 15; schema: Section 24.

This is the system's first role whose permissions are filtered by data ownership (team membership) rather than granted/withheld outright — every other role in Section 15 is scope-free once a permission is granted. Resolved by Q19: rather than splitting "Manager" into its own distinct role, its "(+Manager)" label was dropped from the base role entirely — Team Leader is the one supervisory tier.

Question 17 ✅ Decided

Section 24's confirmation #4 flagged Promotions (bundle/buy-X-get-Y) as schema-undefined — neither source document says what one needs. What's the model?

DecisionTwo promotion types sharing one schema: promotions, promotion_items, promotion_rewards. Bundle — buy an exact set of components (product/category/collection + quantity, in promotion_items) for a special price (fixed_price, percentage, or fixed_amount off). Buy X Get Y — buy a qualifying quantity (trigger, in promotion_items), get a reward item (in promotion_rewards) free or discounted; the reward item must already be in the cart, it's never auto-added. Both are auto-applied server-side at cart/checkout, no code required (unlike coupons); priority resolves overlaps, and stackable_with_coupons controls whether a coupon can also apply. Full schema and flow: Section 24.

Authored by the Vice Chairman role, which already listed "promotions" among its responsibilities (Section 15) — no new role needed. Order-level traceability via a new order_items.promotion_id (Section 24); returns/refunds need no special handling since they work off what was actually charged.

DecisionRole-scoped, mapped explicitly per role. Full role-by-role mapping (9 rows, one per base role): Section 14. No new tables — every widget reads existing data (orders, inventory, treasury, catalog).

This is a data-layer decision only — which query runs, not how the dashboard looks. Section 14's existing "screen design deferred to a follow-up conversation" callout still stands; the widget layout is unspecified, only what data each role's Dashboard Index is allowed to return.

Question 19 ✅ Decided

Now that Customer Service Team Leader exists (Q16), should Customer Service (+ Manager) stay merged, split into a third role, or something else?

DecisionDrop the "(+ Manager)" label — the role is renamed to just Customer Service. No third role is added. Customer Service Team Leader becomes the department's one and only supervisory tier, so the "Manager" half of the old merged name is redundant. The base Customer Service role's actual permissions and visibility are unchanged (global, unscoped) — this is a naming/org-model simplification, not an access change. orders.create on /admin/orders/create (Section 08) now reads "Customer Service and Customer Service Team Leader roles."

Other option considered: splitting "Manager" into its own third role, sitting above Team Leaders — rejected as unnecessary complexity; nothing in either source document calls for a role above Team Leader within Customer Service specifically, and department-wide oversight already exists via Chairman/Super Admin. Resolves the open item both Section 15 and Q16 flagged.

Question 20 ✅ Decided

How should the active locale actually be determined at request time — a session/cookie value, or something visible in the URL?

DecisionURL prefix, enforced by a SetLocale middleware. Every storefront and admin route is wrapped in a {locale} route-group segment — /ar/… / /en/… for the storefront, /ar/admin/… / /en/admin/… for admin. The middleware reads that segment, validates it, and calls App::setLocale() — the URL is the single source of truth for which language renders, not a hidden session value. A bare / redirects to /ar/ by default (or the visitor's last explicit choice, via a lightweight preference cookie); the locale switcher navigates to the sibling URL rather than re-rendering the same one. Full mechanism: Section 16.

Other option considered: session/cookie-only locale (no URL change) — rejected because it makes every page un-shareable and un-crawlable in a specific language, which matters for an e-commerce storefront's SEO more than for the admin side. Applied identically to both areas per Section 16's "never a separate architecture" principle; admin's /en/admin/… path exists from day one but stays gated until Question 2's English-for-staff toggle.

✅ Decided — schema-wide conventions

Confirmed by the project owner. These apply to every table below; neither source document stated them explicitly, but they're no longer open:

  • Primary keys: bigint unsigned auto_increment everywhere (Laravel's default). Nothing needs a UUID for external exposure — the customer-facing order_number (Section 10) already serves that role for orders, and no other table is referenced by ID in a public URL.
  • Timestamps: every table gets created_at/updated_at (Laravel's standard columns) unless noted — omitted from the field lists below rather than repeated 40+ times.
  • Soft deletes: deleted_at added only on the seven models Section 23 named — products, categories, orders, customers, employees, returns, treasuries.
  • Money: decimal(10,2) throughout. EGP has 100-piastre subunits, so 2 decimal places is enough.
  • Translatable columns (marked * below, e.g. products.name*): spatie/laravel-translatable stores these as one json column per field ({"en":"...","ar":"..."}) on the table itself — not a separate translations table. Section 18's entity list names "translations" as if it were its own table; it isn't, and this corrects that.
  • Nullability: every table below now states it explicitly. Single-entity tables (one row per field) carry a dedicated Null column (No = required, Yes = nullable). Combined tables (several small tables sharing one field-list cell) mark a nullable field inline as field_name (null) — a field with no such marker is required. Foreign keys are required unless the relationship is genuinely optional (an assignment before it's made, an amount before it's collected, etc.).

Two flows: how a promotion is authored, and how it's evaluated against a live cart. Both are server-side — the frontend only ever displays what the server already decided, same principle as shipping and coupon pricing (Section 02).

Authoring — Vice Chairman (Section 15)
Open Promotions → New
↓
Pick type
↓
Bundle
Add required components (product / category / collection + quantity) → promotion_items
↓
Set bundle discount — fixed_price, percentage, or fixed_amount
Buy X Get Y
Add trigger items + minimum quantity → promotion_items
↓
Add reward items + quantity → promotion_rewards; set reward discount — free, percentage, or fixed_amount
↓ both converge
Set dates, priority, usage limits, stackable_with_coupons
↓
Activate
Evaluation — cart & checkout, server-side only
Cart contents (or checkout review)
↓
Scan active promotions — is_active, within starts_at/ends_at, under usage_limit
↓
Cart satisfies a promotion's promotion_items quantities?
↓
No match
no discount, nothing shown
Bundle matched
discount applied to the matched components' subtotal
Buy X Get Y matched
discount applied to matching reward item(s) already in the cart, up to reward quantity × complete trigger multiples
Buy X Get Y never auto-adds the reward item to the cart — the customer must already have a qualifying reward item in it for the discount to apply to.
↓
Cart qualifies for more than one promotion on overlapping items? Highest priority wins for those items; the rest are skipped — no stacking two promotions on the same line
↓
Coupon (if entered) applied afterward, only if the winning promotion's stackable_with_coupons allows it
↓
Totals recalculated server-side → order created; each discounted order_items row records its promotion_id

Returns/refunds need no special handling — a returned item's refund is based on what was actually charged (Section 12), which already reflects any promotion discount baked into order_items.unit_price/subtotal at order time.
