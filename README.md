# WAQAR — Fashion E-Commerce Platform

A single-store fashion e-commerce platform (Laravel · Inertia.js · React · TypeScript · Tailwind CSS) with a full customer storefront and a complete internal operations layer underneath — order checking, delivery management, accounting, treasury, and employee management — on the same orders/products/inventory, without changing the customer's shopping experience.

## Documentation

Everything about *what* this system is and *how* it's built is recorded in two documents — update those first, this file only tracks *progress*:

- [`PROJECT-SYSTEM-DOCUMENTATION.html`](PROJECT-SYSTEM-DOCUMENTATION.html) — the full specification: unified customer + internal flow, product/inventory/order/shipping/returns model, roles & permissions, i18n, database schema (Section 24), and the 21 decisions made along the way (Section 22).
- [`WAQAR-DELIVERY-ROADMAP.html`](WAQAR-DELIVERY-ROADMAP.html) — the 9-phase build sequence (also mirrored as Section 25 of the spec above).
- [`DEPLOYMENT.md`](DEPLOYMENT.md) — how to stand the system up, and the cutover checklist to walk before it takes a real customer's money. Most of it is executable: `php artisan waqar:preflight`.

## Stack

| Layer | Technology |
|---|---|
| Backend | Laravel 12, PHP 8.3+ |
| Database | MySQL 8+ |
| Frontend runtime | React 19 + TypeScript via Inertia.js |
| Styling | Tailwind CSS v4 (storefront) · Bootstrap 5.3.3 + react-bootstrap (admin) — never both on one page |
| Auth / Authorization | Laravel Auth + spatie/laravel-permission (9 base roles + `Store Orders`; three of them data-scoped) |
| Media | spatie/laravel-medialibrary |
| Audit log | spatie/laravel-activitylog |
| Cache / Queue / Session | Redis (phpredis extension, no predis package) |
| Translations | spatie/laravel-translatable (Arabic + English), URL-routed via `/ar/…` / `/en/…` (Phase 6) |
| Payment | Cash on Delivery only |
| Local environment | Docker Compose — `app` (PHP-FPM + Node), `nginx` (`:26991`), `mysql`, `redis`, `phpmyadmin` (`:32231`) |

## Getting started

```bash
docker compose up -d --build
```

Storefront: `http://localhost:26991` (redirects to `/ar`) · Admin: `http://localhost:26991/ar/admin` · phpMyAdmin: `http://localhost:32231` · Mail catcher: `http://localhost:32232`

The `app` container runs php-fpm, two Redis queue workers and the scheduler under supervisord (Phase 8), so
customer notifications are queued rather than sent inside the request. `php artisan waqar:preflight` checks
whether a deployment can actually take an order — run it after every deploy.

Every page lives under a `{locale}` prefix since Phase 6 — `/ar/…` and `/en/…` — and a bare URL redirects
into the visitor's language. `tools/check-translations.py` guards both apps against missing keys.

`.env` already exists (git-ignored) and points at the Docker services; a fresh clone can regenerate it from `.env.example` the same way. One-off `artisan`/`composer`/`npm` commands run inside the `app` container:

```bash
docker compose run --rm app php artisan migrate
docker compose run --rm app npm run build
docker compose run --rm app ./vendor/bin/pest
```

The Pest suite runs against its own database (`waqar_testing`), created on the first boot of a fresh
`mysql` volume — it is **not** the development database, because `RefreshDatabase` drops every table it
touches. See `tests/TestCase.php` for why that override lives in PHP rather than in `phpunit.xml`.

If a command needs to write a *new* file into the repo (installing a package, publishing a vendor file, generating a migration), see the file-ownership note in the latest `PHASE-<n>-HANDOVER.md` — those were run as `--user root` and need a `chown` pass back to the host user afterward.

- **2026-09-14** — **Light/dark mode, the way Larkon ships it.** The topbar gained the template's own `#light-dark-mode` switch, which does one thing: flip `data-bs-theme` on `<html>`. app.min.css is compiled twice over (`:root,[data-bs-theme=light]` and `[data-bs-theme=dark]`), so every Larkon component follows from that attribute alone — and the topbar follows too without touching `data-topbar-color`, because Larkon groups `html[data-bs-theme=dark][data-topbar-color=light]` with its own dark topbar block. Two departures from its `app.js`: the choice persists in **localStorage** rather than the `sessionStorage` `__LARKON_CONFIG__` blob (matching how the sidebar size is already remembered — sessionStorage forgets a preference this visible every time the tab closes), and the *initial* value is restored by the blocking script in `admin.blade.php`, not in React, which mounts after first paint and would otherwise flash the light theme for a frame on every load for anyone who picked dark. The brand palette does **not** follow for free, for two separate reasons. The `:root` override block is (0,1,0) and loads after app.min.css, so it outranks Bootstrap's own `[data-bs-theme=dark]` block at equal specificity — light-mode link and emphasis colours would have carried straight into dark mode; everything is now restated under `html[data-bs-theme='dark']` (0,1,1) to take that back. And the primary **is** a very dark navy: #012c4e against Larkon's dark body measures **1.04:1**, so a primary button would have been a navy rectangle on a near-identical background. Dark mode therefore keeps the brand hue (207°) and raises the lightness — #0c6fc0 for fills (white text on it 5.2:1) and #5eaded for text and links (6.1:1). Those have to be two values, not one: text on the dark card needs luminance above ~0.30 to clear 4.5:1 and white-on-fill needs it below ~0.18, so no single colour clears both, which is exactly why Bootstrap splits `--bs-primary` from `--bs-primary-text-emphasis`. Bootstrap's own recipe — tint the primary 40% toward white — lands navy at #678095 and **3.9:1**, failing AA, so the tint is taken further here. Checking the result rather than assuming it caught one more: `.text-primary` resolves `--bs-primary-rgb`, now the *fill* value, leaving the dashboard's tile icons **navy-on-navy at 2.6:1** — restated with `!important`, since Bootstrap writes its colour utilities that way and specificity alone cannot outrank them. The sidebar is deliberately unaffected by the mode: `html[data-menu-color=dark]` keeps it brand navy with its cream active bar in both, which needed the six-class sidebar rule restated under the dark prefix so the dark `.nav-link.active` rule would not undo it. Verified against computed styles in both modes and both locales — toggled by clicking the real button, not by scripting the attribute — plus persistence across a full document load. 157 tests (1045 assertions), Pint · Larastan · tsc · ESLint · Prettier · 0 missing keys all clean, **49/49 admin pages render**.

- **2026-09-14** — **Product SKUs are assigned, not typed.** The create form's SKU field is now disabled and pre-filled with the value the product will actually get, from a new `SkuGenerator` (`app/Services/Catalog`). Three things there were not the obvious one-liner. The number **continues the existing sequence** rather than counting rows — `count() + 1` repeats a number the moment anything is deleted, and the column is UNIQUE, so that lands as a `QueryException` on save. It scans **trashed products too**: `products.sku` is UNIQUE and `Product` is soft-deleted, so a deleted product still owns its SKU in the index, and generating against live rows only would hand out a number the database then refuses — the same shape of bug as Phase 4's shipping-rate revive, and pinned by its own test. And `store()` **generates its own value inside the transaction rather than reading the request**: a disabled field is a UI affordance, not a guarantee, and doing it at insert time rather than at page-open means two operators who opened the form together don't both save the same number. A test posts `sku: HACKED-001` and asserts the product comes out as `PRD-015` with no such row anywhere. Prefix: the seeded SKUs are hand-picked mnemonics (MSH = Mesh Shirt, BLU = Off-the-Shoulder *Blouse*) that skip words and take letters from inside them, so **no mechanical rule reproduces them**; rather than approximate one that would sometimes agree and sometimes not, generated SKUs take one fixed prefix and carry the convention in the part that has to be unique. Nothing parses the prefix, so the existing mnemonics stay valid alongside. Editing an existing product still allows a correction — an assigned SKU is a starting value, not a permanent one. Two Phase 4 tests that looked products up by the SKU they had posted now look them up by slug, since the request no longer decides. 3 new tests (**160/1059 total**), Pint · Larastan · tsc · ESLint · Prettier · 0 missing keys all clean, 49/49 admin pages render.
